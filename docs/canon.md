# 📜 Канон: Харис

Архитектурные решения, зафиксированные в stone. Не пересматривать без весомых причин.

## A001: Чистый Three.js, без фреймворков

**Решение:** Использовать Three.js напрямую, без React Three Fiber, PlayCanvas и т.п.

**Причины:**
- Минимальный размер бандла (важно для Yandex Games)
- Полный контроль над циклом рендера
- Нет дополнительного абстракционного слоя
- Простое обновление до новых версий Three.js

**Отклонено:**
- React Three Fiber — избыточная абстракция, увеличивает бандл
- PlayCanvas — тяжёлый, ориентирован на другие сценарии
- Phaser — 2D-движок, не подходит для 3D

## A002: Автоприцел как основная механика

**Ререшение:** Игрок всегда стреляет в ближайшего врага автоматически. Ручная наводка — опционально в будущем.

**Причины:**
- Нулевой порог входа
- Снижает сложность управления (важно для мобильных)
- Фокус на позиционировании и уклонении, а не на точности стрельбы
- Быстрый геймплей без долгого обучения

**Отклонено:**
- Ручная наводка — требует доп. управления (мысенаводка/джойстик)
- Гибрид (авто + модификатор ручного) — усложняет код

## A003: Object Pooling для всех динамических объектов

**Решение:** Снаряды, враги, частицы — все используют object pool. Ноль аллокаций в игровом цикле.

**Причины:**
- 60 FPS на мобильных устройствах
- Нет GC-пауз во время боя
- Предсказуемое потребление памяти (< 200MB)
- Простое управление пиковыми нагрузками (волна 20 врагов)

**Отклонено:**
- Простое create/destroy — приводит к GC и фризам
- ECS-архитектура — избыточно для MVP, больше кода

## A004: State Machine для игровых сцен

**Ререшение:** Явный GameState с конечным автоматом: BOOT → MENU → WAVE_START → COMBAT → WAVE_COMPLETE → GAME_OVER / VICTORY.

**Причины:**
- Чёткие переходы между состояниями
- Нет некорректных комбинаций (например, бой в меню)
- Простая отладка и тестирование
- Легко добавлять новые состояния

**Отклонено:**
- Флаги (isPlaying, isPaused...) — состояния расползаются
- Вложенные состояния — сложнее в отладке

## A005: InstancedMesh для однотипных врагов

**Решение:** Враги одного типа рендерятся через InstancedMesh.

**Причины:**
- 1 draw call на тип вместо N
- Пик 20 врагов на экране — 20 draw calls → 4 (Runner, Shooter, Tank, Miniboss)
- Меньше нагрузка на GPU
- Поддержка InstancedMesh в Three.js r125+

**Отклонено:**
- Индивидуальные Mesh для каждого врага — draw calls взлетают до 100+
- GPU SkinnedMesh для всех — избыточно для MVP

## A006: Процедурная геометрия, без текстур и ассетов

**Решение:** Все модели генерируются процедурно из примитивов BoxGeometry, SphereGeometry, CylinderGeometry. Цвета — через материалы. Окружение — шейдеры.

**Причины:**
- Нулевой размер ассетов
- Быстрая итерация по визуалу
- Масштабируемость под разные разрешения
- Нет проблем с загрузкой ресурсов

**Отклонено:**
- 3D-модели из Blender — увеличивают размер бандла
- Текстуры — увеличивают размер, требуют обработки
- Skeleton-анимации — избыточно для геометрических форм

## A007: Внутренние коллизии через AABB

**Решение:** Все коллизии проверяются через AABB (axis-aligned bounding box).

**Причины:**
- 2D-плоскость движения (нет вертикальных коллизий)
- Простая математика — быстрая проверка
- Нет необходимости в полноценной физике
- Проще дебажить и настраивать

**Отклонено:**
- Three.js Raycasting — медленнее, сложнее
- Cannon.js / Ammo.js — избыточная зависимость, бандл
- SAT collision — не нужна для прямоугольников/сфер

## A008: Все данные баланса в config.js

**Решение:** Все числовые параметры (HP, скорость, урон, количество врагов) вынесены в один объект CONFIG.

**Причины:**
- Единое место для балансировки
- Легко менять значения без поиска по коду
- Возможность горячей настройки во время дев-тестов
- Простота создания «уровней сложности» в будущем

**Отклонено:**
- Хардкод в классах — невозможно быстро балансировать
- Внешний JSON для конфига — дополнительный шаг загрузки

## A009: Vite как сборщик

**Решение:** Vite 5.x для dev-сервера и прод-сборки.

**Причины:**
- Мгновенный HMR (горячая замена модулей)
- Маленький бандл через esbuild/tree-shaking
- Простая конфигурация
- Статический экспорт для Yandex Games
- Поддержка ES modules нативно

**Отклонено:**
- Webpack — медленный, сложная конфигурация
- Rollup напрямую — нет dev-сервера
- Parcel — менее предсказуемое tree-shaking
- Без сборщика (CDN Three.js) — медленная загрузка, нет HMR

## A010: Деградация качества при низком FPS

**Решение:** Автоматическое снижение качества: частицы, тени, post-processing отключаются при FPS < 30.

**Причины:**
- Yandex Games включает мобильные устройства
- Цель: играбельность в ущерб визуалу
- Игрок может играть даже на слабом устройстве
- Нет ручных настроек качества (MVP)

**Отклонено:**
- Ручной выбор качества — лишний шаг для игрока
- Динамическое разрешение — сложнее реализовать
- Фиксированное качество — отсекает аудиторию
